길 건너기 게임 제작 과정

이미 있는 작은 게임 하나를 똑같이 만들면서 0 준비부터 G 정리까지 AI와 나눠 일한 기록이다. 그림은 모두 도형으로 그렸고, 원작의 그림과 소리는 쓰지 않았다.

게임 해 보기 캐릭터 모두 풀고 해 보기 게임 1 폴더 (문서·작업 과정)

왜 만들었나

내 말

창작 게임을 만들기 전, 기존에 흥행한 게임을 분석해보고 이를 모방하는 것으로 게임 만들기의 기본을 익히고 좋은 게임의 조건을 분석하여 발전된 게임을 만드는 것을 목표로 한다.

단계마다 한 일

단계마다 끝나는 기준을 정해 두고, 기준을 하나씩 확인한 뒤에 다음 단계로 넘어갔다. 인용 칸은 그날 로그에 내가 쓴 문장이다 (README 와 같게 말투만 맞췄다).

  1. 0

    준비

    GitHub 저장소를 연결하고, 작업을 시작하고 끝낼 때 쓰는 명령(/start, /end)으로 하루를 이어받는 흐름을 확인했다. AI 작업 규칙 한 줄을 내 말로 고쳤다: "시작 전에 '변경될 방향 및 결과'를 간단히 서술하고 확인받는다."

  2. A

    출발점

    원작은 내가 해 본 게임에서 골랐다 (원작 후보는 AI가 먼저 내지 않았고, 고른 뒤 원작 조작 검색과 의견을 맡겼다). 원작을 해 보고 규칙, 조작, 수치, 반응, 어려워지는 방식을 본 것과 짐작한 것으로 나눠 적었다. 원작과 다르게 할 것으로 개구리(15번 연속 전진하면 풀림, 두 칸 점프), 황소(차에 30번 치이면 풀림, 한 판에 한 번 막아 줌), 한 번 밟으면 사라지는 발판을 넣었다.

    내 말AI를 통해서 처음으로 만들어 볼 게임의 원본 게임을 정하고 그 게임의 구조 및 플레이 방식에 대해서 다각도로 고찰했다.
  3. B

    정의

    상황, 문제, 목표를 내 말로 쓰고, 남이 읽고 됐는지 가릴 수 있는 끝나는 기준을 정했다. 게임 오버는 네 경우(차·열차에 부딪힘이나 물·빈 공간에 빠짐, 뒤로 4번 연속, 다가오는 붉은 선, 발판을 탄 채 화면 옆 끝)로 못 박았다. reviewer 가 세 번 보고서야 기준을 채웠다.

    내 말잘못되었던 게임 오버 규칙(한 칸 움직일 때마다 배경이 움직여 게임 오버에 가까워짐)을 수정하였고, reviewer를 여러 번 활용하여 끊임없이 검토를 요청하여 잘못된 점을 찾아내어 수정할 수 있었다.
  4. C

    쪼개기

    핵심 루프를 한 줄로 쓰고 작업 8개로 나눴다. 미뤄 둔 수치(한 판 시간, 뒤처짐 선, 황소 범위 등)는 AI가 낸 후보 가운데 내가 고르고 이유를 결정 기록에 남겼다. 엔진은 칸 단위 2D 라 웹(HTML과 자바스크립트)으로 정했다.

    내 말게임 내 세부 규칙을 설계했다.
  5. D

    첫 판

    작업 1을 먼저 만들어 확인하고(AI 9분), 2~8은 한 번에 만들되 작업마다 따로 열어 볼 수 있게 남겼다(AI 22분). 해 보고 찾은 고칠 점은 세 묶음으로 고쳤다(AI 약 16분). AI는 게임을 실행할 수 없어서 브라우저 없이 규칙을 검사하고(176개), 바로 앞 줄만 보고 움직이는 봇으로 건널 수 있는 판인지 쟀다. 화면, 소리, 손맛은 내가 봤다.

    내 말요청에 따라 빌드된 게임의 기능들을 직접 확인하며 설계한 대로 완성되었는지 확인하였다. 또한 실제로 플레이해 보았을 때 개선점이 있다면 이를 반영하여 더 나은 결과물을 도출해내도록 하였다.
  6. E

    올리기

    저장소를 공개하고 GitHub Pages 로 링크를 만들어 PC 와 휴대폰에서 열리는 것을 확인했다. 최고 기록을 넘기는 순간의 팡파레와 "PC 키보드 전용" 표시를 더했다.

    내 말추가 수정 사항 몇 가지를 추가하고 게임 링크 오픈 형태로 전환했다.
  7. F

    다듬기

    처음 보는 사람 1명(20대, PC 키보드)이 설명 없이 결과창까지 갔다. 지적은 차 판정과 통나무 판정이었다. 이것을 출발점으로 작업 15~25를 하나씩 고치고 매번 직접 해 봤다: 차 판정을 그림 폭에 맞춤, 통나무에 올라탈 때 비스듬히 가지 않게, 뒤로 4번이면 새가 낚아챔, 차와 열차 소리의 무게, 개구리 조작, Esc 일시정지.

    플레이 메모 (내 말)차에 치이는 판정이 보이는 것보다 빡빡해서 플레이에 있어서 불쾌감을 겪었다. 특히 차가 지나간 후에 뒷부분에 치이는 경우가 많았다.
    내 말테스터에게 나의 게임을 플레이하도록 하고, 피드백을 받아 이를 수정하였다.
  8. G

    정리

    README 를 채우고 회고를 했다. 로그와 장부에서 반복된 막힘을 세고, 그동안 고친 작업 규칙마다 효과가 있었는지 판정했다. 모바일 조작은 넣지 않기로 정했다. 마지막으로 그래픽을 다듬었다. 돌 그림에만 있던 방식(바닥 그림자, 같은 색 계열의 진한 테두리, 밝은 윗면과 어두운 아랫면)을 나무, 차, 열차, 통나무, 캐릭터, 바닥까지 넓혔고, 그림의 가로 바깥 끝(판정에 쓰는 끝)은 그대로 두어 판정은 바뀌지 않았다. 해 보고 통나무 끝을 둥글게 고치고 기본 캐릭터 볼의 주황 줄을 뺐다.

    새로 할 수 있게 된 것 (내 말)게임의 기본적인 동작 매커니즘을 익혀 이후 게임 개발의 이해도를 높일 수 있었다.

AI와 나눈 일

내가 맡은 것

  • 무엇을 만들지, 재미와 방향 정하기
  • AI가 낸 후보 가운데 고르고 이유 남기기
  • 직접 해 보고 됐는지 안 됐는지 판단하기
  • 테스터에게 시키고 플레이 메모 쓰기
  • 문제 정의, 고른 이유, 로그의 내 칸은 내 말로

AI(Claude Code)에게 맡긴 것

  • 게임 코드 쓰기와 고치기
  • 브라우저 없이 규칙을 검사하는 도구와 봇
  • 바꿀 방향을 후보 표와 추천으로 내기
  • 결정 기록, 작업 표, 장부 정리
  • 기록을 모아 이 페이지로 정리
  • reviewer: 만든 과정을 보지 않은 눈으로 검토

AI가 틀린 곳과 잡은 방법

AI의 결과를 고치게 하거나 같은 설명을 다시 한 일, 틀린 것을 찾은 일은 그 자리에서 장부에 한 줄씩 적었다. 게임 1 에서 31줄이 쌓였다.

내가 잡아 고치게 함 19 reviewer 가 찾음 7 AI가 스스로 찾음 3 내가 틀린 일 2
  • C
    내 말규칙에 대한 누락 지점이 중간중간에 발생하였고, 이를 지속적인 reviewer 사용을 통한 끊임없는 확인을 통하여 바로잡았다. 해금한 캐릭터의 플레이 방식을 통하여 캐릭터를 해금할 수 있냐는 다소 엉뚱한 물음을 바로잡아주거나, 필요한 규칙이 누락되었을 때 수동으로 적어주는 상황이 존재하였다.
  • D
    내 말AI는 장애물의 움직임을 미리 알고 있다는 가정 하에 플레이어가 대처 불가능한 상황이 나오지 않는다고 보고하였지만, 실제로 플레이어는 장애물을 포착하고 나서부터 대처할 수 있기에 이는 잘못된 판단이었다.
  • F
    내 말이전에 만들어 놓은 규칙 중 변경점이 있을 시 이전의 문서에서 해당 내용을 탐색하여 일괄 변경한다는 점을 누락한 것을 확인하고 지적하여 수정하였다.

규칙 변화 기록

장부에 같은 종류가 두 번 쌓이면 AI 작업 규칙을 한 줄 고치자고 제안받고, 내가 고르거나 범위를 좁혀서 넣었다. 회고에서 고친 뒤에 같은 막힘이 몇 번 나왔는지 세어, 두 번 이상이면 효과 없음으로 판정했다. 효과가 없던 둘은 규칙을 더 늘리지 않고, 저장 전에 reviewer 를 권하는 범위를 넓히는 쪽으로 바꿨다. 게임 1 과 관계없는 두 줄(게임 2 에서 나온 규칙, 두 게임 병행 요청)은 싣지 않았다.
